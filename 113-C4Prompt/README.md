# 온라인 쇼핑몰 C4 다이어그램 — 레벨별 프롬프트 가이드

AI(Claude, ChatGPT 등)에게 **어떤 프롬프트를 순서대로 주면** 온라인 쇼핑몰의 C4 모델 Level 1~4와 조별 리뷰 자료를 만들 수 있는지 정리한 가이드입니다.

| 단계 | 과제 | 산출물 |
|---|---|---|
| 0 | 공통 맥락 설정 | 쇼핑몰 가정·표기 규칙 |
| Level 1 | 사용자와 외부 시스템(결제, 배송, 재고)을 찾아 System Context 작성 | `L1-context` 다이어그램 + 설명 |
| Level 2 | 웹 앱, 모바일 앱, DB 등 컨테이너와 통신 관계 표시 | `L2-container` 다이어그램 |
| Level 3 | 컨테이너 하나를 골라 컴포넌트와 상호작용 표시 | `L3-component` 다이어그램 |
| Level 4 | 핵심 컴포넌트 하나의 주요 클래스와 의존성 표시 (선택) | `L4-code` 클래스 다이어그램 |
| 리뷰 | 표기 일관성, 상세 수준, L1을 비개발자가 바로 이해하는지 점검 | 리뷰 체크리스트·수정 제안 |

---

## 사용 방법

1. **한 대화(세션) 안에서** 0 → L1 → L2 → L3 → L4 → 리뷰 순서로 프롬프트를 이어서 입력합니다. 앞 단계의 결과를 AI가 기억해야 레벨 간 이름과 관계가 일관됩니다.
2. 대화를 새로 시작해야 한다면, 직전 레벨의 다이어그램 코드를 프롬프트 맨 앞에 붙여 넣고 "이 다이어그램을 기준으로"라고 덧붙이세요.
3. 결과 코드는 [Mermaid Live Editor](https://mermaid.live) 또는 GitHub Markdown(` ```mermaid ` 블록)에 붙여 넣어 렌더링합니다. PlantUML을 선호하면 프롬프트의 "Mermaid C4"를 "C4-PlantUML"로 바꾸세요.
4. `[ ]` 안의 내용은 조별로 바꿔 쓰는 부분입니다.

---

## 0단계 — 공통 맥락 설정 프롬프트

모든 레벨에서 같은 이름·같은 표기를 쓰도록 먼저 규칙을 고정합니다.

```text
너는 소프트웨어 아키텍트야. 지금부터 "온라인 쇼핑몰"을 C4 모델(Level 1~4)로 단계별로 표현할 거야.

[시스템 가정]
- 서비스명: [우리쇼핑]
- 사용자: 고객(구매자), 판매자/운영자(관리자)
- 외부 시스템: 결제 대행(PG), 배송사(택배 API), 재고/물류 관리 시스템(WMS), 이메일·SMS 알림 서비스
- 채널: 웹, 모바일 앱(iOS/Android)

[표기 규칙 — 모든 레벨에서 반드시 지켜줘]
1. 다이어그램은 Mermaid C4 문법(C4Context, C4Container, C4Component)으로 작성하고, Level 4는 Mermaid classDiagram으로 작성해.
2. 요소 이름은 한 번 정하면 모든 레벨에서 동일하게 사용해(예: "결제 대행사(PG)"를 다른 곳에서 "Payment Gateway"로 바꾸지 말 것).
3. 모든 요소는 [이름, 유형/기술, 한 줄 설명]을 갖고, 모든 관계 화살표에는 "동사 + 목적어" 라벨을 붙여(예: "결제를 요청한다").
4. 기술 스택은 Level 2부터 표기하고, Level 1에는 기술 용어를 쓰지 마.
5. 각 다이어그램 아래에 범례(Legend)와 "요소 목록 표(이름 | 유형 | 설명)"를 붙여.

이해했으면 위 가정을 요약하고, 빠진 외부 시스템이나 사용자가 있으면 제안만 해줘. 아직 다이어그램은 그리지 마.
```

> 💡 **팁**: AI가 제안한 추가 요소(예: 쿠폰/포인트 시스템, 고객센터)를 넣을지 조에서 결정한 뒤 "OO는 포함, OO는 제외"라고 답해 범위를 확정하세요.

## Level 1 — System Context 프롬프트

**목표**: 쇼핑몰 시스템을 하나의 상자로 보고, 누가(사용자) 쓰고 어떤 외부 시스템(결제·배송·재고)과 주고받는지 표현. **비개발자도 바로 이해할 수 있어야 함.**

```text
Level 1 System Context 다이어그램을 만들어줘.

[요구사항]
- 쇼핑몰 시스템 전체를 하나의 System 상자로 표현해(내부는 보여주지 마).
- 사람(Person): 고객, 판매자/운영자
- 외부 시스템(System_Ext): 결제 대행(PG), 배송사, 재고/물류 시스템(WMS), 알림 서비스
- 각 관계에는 "무엇을 주고받는지"를 일상 언어로 적어줘(예: "결제를 요청하고 승인 결과를 받는다").
- 기술 용어(API, REST, DB, 서버 등)는 쓰지 마. 비개발자(기획자, 경영진)가 읽는다고 가정해.
- 요소는 최대 8개 이내로 유지해.

[출력 형식]
1. Mermaid C4Context 코드
2. 요소 목록 표 (이름 | 유형 | 설명)
3. 다이어그램을 3문장으로 설명하는 요약문 (비개발자용)
4. 자체 점검: 기술 용어가 섞였는지, 화살표 라벨이 빠진 곳이 있는지 확인 결과
```

**확인 포인트**
- [ ] 결제·배송·재고 외부 시스템이 모두 있는가?
- [ ] 쇼핑몰 내부(웹/앱/DB)가 드러나 있지 않은가?
- [ ] 화살표 라벨이 "데이터 전송" 같은 모호한 표현이 아닌가?

---

## Level 2 — Container 프롬프트

**목표**: 쇼핑몰 시스템 상자를 열어 웹 앱, 모바일 앱, API 서버, DB 등 **실행/배포 단위**와 그 사이 통신을 표시.

```text
방금 만든 Level 1의 "[우리쇼핑]" 시스템 상자를 열어서 Level 2 Container 다이어그램을 만들어줘.

[요구사항]
- Level 1의 사람·외부 시스템 이름을 그대로 재사용하고, 시스템 경계(System_Boundary) 안에 컨테이너를 배치해.
- 최소 포함 컨테이너:
  - 웹 앱(SPA) 
  - 모바일 앱(iOS/Android)
  - API 서버(백엔드 애플리케이션)
  - 관리자(백오피스) 웹
  - 주 데이터베이스(ContainerDb)
  - [선택] 캐시, 메시지 큐, 검색 엔진 — 필요하다고 판단하면 이유와 함께 추가
- 각 컨테이너에 기술 스택을 적어줘(예: "React", "Spring Boot", "PostgreSQL"). 기술 스택: [조에서 정한 스택, 없으면 일반적인 선택으로].
- 각 관계에 "목적 + 프로토콜"을 적어줘(예: "주문 정보를 조회한다 [HTTPS/JSON]", "주문 완료 이벤트를 발행한다 [AMQP]").
- 외부 시스템(PG, 배송사, WMS, 알림)과 연결되는 컨테이너가 어디인지 명확히 해.

[출력 형식]
1. Mermaid C4Container 코드
2. 컨테이너 목록 표 (이름 | 기술 | 책임)
3. 통신 관계 표 (출발 → 도착 | 목적 | 프로토콜 | 동기/비동기)
4. Level 1과 이름이 달라진 요소가 있는지 자체 점검 결과
```

**확인 포인트**
- [ ] 컨테이너 = "따로 배포·실행되는 단위"인가? (클래스나 모듈이 섞이지 않았는가)
- [ ] 모든 화살표에 프로토콜이 표기됐는가?
- [ ] Level 1의 외부 시스템이 빠짐없이 연결됐는가?

## Level 3 — Component 프롬프트

**목표**: 컨테이너 **하나**를 골라 내부 컴포넌트와 상호작용을 표시. 쇼핑몰에서는 보통 **API 서버**가 가장 의미 있는 선택입니다.

```text
Level 2의 컨테이너 중 "[API 서버]"를 골라 Level 3 Component 다이어그램을 만들어줘.

[요구사항]
- Container_Boundary 안에 컴포넌트를 배치하고, 경계 밖의 다른 컨테이너(웹 앱, 모바일 앱, DB)와 외부 시스템(PG, 배송사, WMS)은 Level 2 이름 그대로 표시해.
- 쇼핑몰 핵심 도메인 기준으로 컴포넌트를 나눠줘. 예시:
  - 회원/인증 컴포넌트
  - 상품 카탈로그 컴포넌트
  - 장바구니 컴포넌트
  - 주문 컴포넌트
  - 결제 컴포넌트 (PG 연동)
  - 배송 컴포넌트 (배송사 연동)
  - 재고 컴포넌트 (WMS 연동)
- 각 컴포넌트에 [이름, 기술(예: Spring @Service), 책임 한 줄]을 적어줘.
- "고객이 주문하기 버튼을 누른 뒤 결제 완료까지" 흐름에 관여하는 상호작용이 화살표로 드러나야 해.
- 컴포넌트는 10개 이하로 유지하고, 유틸리티·설정 같은 부수적인 것은 제외해.

[출력 형식]
1. Mermaid C4Component 코드
2. 컴포넌트 목록 표 (이름 | 기술 | 책임 | 의존하는 컴포넌트)
3. "주문 → 결제" 시나리오를 번호 매긴 단계로 설명 (다이어그램의 화살표와 1:1 대응)
4. 이 컨테이너를 고른 이유 2~3줄
```

> 💡 다른 조와 겹치지 않게 **모바일 앱**이나 **관리자 웹**을 골라도 됩니다. 이때는 "[API 서버]" 부분과 컴포넌트 예시를 바꾸세요(예: 모바일 앱 → 화면(View), 상태 관리, API 클라이언트, 푸시 수신 컴포넌트).

**확인 포인트**
- [ ] 정확히 한 컨테이너만 펼쳤는가?
- [ ] 컴포넌트가 클래스 수준으로 너무 잘게 쪼개지지 않았는가?
- [ ] 외부 시스템 연동 지점이 어느 컴포넌트인지 보이는가?

## Level 4 — Code(클래스) 프롬프트 (선택)

**목표**: 핵심 컴포넌트 **하나**의 주요 클래스와 의존성 표시. 쇼핑몰에서는 **주문 컴포넌트** 또는 **결제 컴포넌트**를 추천합니다.

```text
Level 3의 "[주문 컴포넌트]"를 골라 Level 4 Code 다이어그램을 만들어줘.

[요구사항]
- Mermaid classDiagram으로 작성해.
- 주요 클래스만 5~10개 포함해. 예시 계층:
  - Controller: OrderController
  - Service: OrderService
  - Domain: Order, OrderItem, OrderStatus(enum)
  - Repository: OrderRepository (interface)
  - 외부 연동 포트: PaymentClient, InventoryClient (interface)
- 각 클래스에 핵심 속성 2~3개, 핵심 메서드 2~3개만 적어줘(getter/setter 제외).
- 관계 유형을 정확히 구분해: 상속(<|--), 구현(<|..), 연관(-->), 의존(..>), 합성(*--).
- Level 3에서 이 컴포넌트가 의존하던 대상(결제 컴포넌트, 재고 컴포넌트, DB)이 어떤 클래스/인터페이스로 이어지는지 보여줘.

[출력 형식]
1. Mermaid classDiagram 코드
2. 클래스 목록 표 (클래스 | 계층 | 책임)
3. 핵심 메서드 placeOrder()의 호출 흐름을 단계별로 설명
4. 의존성 방향이 안쪽(도메인)을 향하는지 자체 점검 결과
```

**확인 포인트**
- [ ] 모든 클래스를 다 그리지 않고 "주요" 클래스만 남겼는가?
- [ ] Level 3의 외부 의존(결제, 재고, DB)과 연결이 맞는가?

## 조별 리뷰 프롬프트

**목표**: 표기 일관성, 상세 수준, L1을 비개발자가 바로 이해하는지 점검.

### ① 표기 일관성 + 상세 수준 점검

```text
지금까지 만든 Level 1~4 다이어그램 전체를 리뷰어 입장에서 점검해줘.

[점검 항목]
1. 표기 일관성
   - 같은 요소가 레벨마다 다른 이름으로 불리는 곳
   - 요소 설명 형식(이름/기술/설명)이 빠지거나 다른 곳
   - 화살표 라벨 형식("동사 + 목적어", 프로토콜 표기)이 어긋난 곳
   - 범례가 없거나 레벨마다 다른 곳
2. 상세 수준(추상화 레벨)
   - L1에 기술 용어나 내부 구조가 새어 나온 곳
   - L2에 컴포넌트/클래스 수준 요소가 섞인 곳
   - L3에 클래스 수준으로 너무 잘게 쪼갠 곳, 또는 반대로 너무 뭉뚱그린 곳
   - L4에 불필요하게 많은 클래스/메서드가 있는 곳
3. 레벨 간 추적성
   - 상위 레벨의 관계가 하위 레벨에서 사라지거나 새로 생긴 곳

[출력 형식]
표: 레벨 | 문제 유형 | 문제 위치(요소/관계) | 설명 | 수정 제안 | 심각도(상/중/하)
마지막에 가장 먼저 고쳐야 할 3가지를 요약해줘.
```

### ② L1 비개발자 이해도 점검

```text
너는 IT 지식이 없는 쇼핑몰 마케팅 팀장이야. Level 1 다이어그램만 보고 다음 질문에 답해줘.
1. 이 시스템은 누구를 위해 무엇을 해주는가?
2. 고객이 물건을 사면 어떤 바깥 회사/시스템들이 관여하는가?
3. 이해가 안 되는 단어나 화살표가 있다면 무엇인가?

답변이 끝나면 다시 아키텍트 역할로 돌아와서,
- 팀장이 막힌 지점을 기준으로 L1 다이어그램을 수정한 Mermaid 코드를 제시하고,
- 수정 전/후 차이를 표로 정리해줘.
```

### ③ 리뷰 반영

```text
리뷰에서 나온 수정 제안 중 [1, 3, 5번]을 반영해서 해당 레벨 다이어그램만 다시 출력해줘.
다른 레벨에 연쇄적으로 바뀌어야 하는 이름/관계가 있다면 그 레벨도 함께 수정하고 변경 목록을 알려줘.
```

| 일관성 | 각 다이어그램에 제목과 범례가 있는가? | |
| 상세 수준 | L1: 시스템 1개 + 사용자 + 외부 시스템만 있는가? | |
| 상세 수준 | L2: 배포 단위(앱, 서버, DB)만 있고 기술 스택이 적혀 있는가? | |

## 프롬프트 작성 요령 요약

- **역할 + 맥락 + 요구사항 + 출력 형식** 4요소를 항상 포함합니다.
- **이전 레벨 이름 재사용**을 매번 명시해야 레벨 간 일관성이 유지됩니다.
- **개수 제한**(L1 8개, L3 10개, L4 5~10개)을 주면 상세 수준이 과해지는 것을 막을 수 있습니다.
- **자체 점검 요청**을 출력 형식에 넣으면 AI가 스스로 누락을 찾아냅니다.
- 결과가 마음에 들지 않으면 처음부터 다시 묻지 말고 "OO 요소를 빼고 OO 관계를 추가해서 다시"처럼 **차이만 지시**합니다.
